这题要严格满足题目要求，不能对每个字符串枚举切分点后再 `O(L)` 判断回文，否则会退化成 `O(ΣL²)`。

可以使用：

> **Manacher 线性预处理回文前后缀 + 反向 Trie**

设所有字符串总长度为 `S`，答案对数量为 `K`，最终复杂度可以做到：

- 时间：**O(S + K)**
- 空间：**O(S)**

其中 `K` 是必须输出的答案数量；极端情况下答案本身就可能达到 `O(n²)`，因此严格来说不可能连输出答案都只花 `O(S)`。

---

## 1. 核心思路

考虑两个字符串：

```text
A + B
```

什么时候是回文？

假设我们把所有字符串 **倒序插入 Trie**。

查询字符串 `A` 时，从左向右沿着 Trie 匹配。

会出现两种情况。

### 情况一：B 比 A 短

例如：

```text
A = abcbaXXX
B = abc 的逆序 = cba
```

如果扫描 `A` 的过程中已经走到了某个字符串 `B` 的结尾：

```text
A = prefix + suffix
B = reverse(prefix)
```

那么：

```text
A + B
= prefix + suffix + reverse(prefix)
```

只需要：

```text
suffix 是回文
```

整个字符串就是回文。

因此查询过程中：

> 如果当前 Trie 节点是某个字符串的结尾，并且 A 剩余部分是回文，那么得到一个答案。

---

### 情况二：B 比 A 长

例如：

```text
A = abcd
B = xxxdcba
```

当整个 `A` 匹配完以后，如果：

```text
B = P + reverse(A)
```

其中：

```text
P 是回文
```

那么：

```text
A + B
= A + P + reverse(A)
```

一定是回文。

因此在 Trie 的每个节点维护：

```text
palList
```

表示：

> 哪些字符串走到当前节点后，剩余的前缀是回文串。

当 `A` 全部匹配完时，把当前节点 `palList` 中的字符串全部加入答案。

## 2. 为什么还需要 Manacher？

普通做法可能这样判断：

```cpp
isPalindrome(word, l, r)
```

一次需要 `O(L)`。

一个长度 `L` 的字符串有 `O(L)` 个切分位置，因此会变成：

```text
O(L²)
```

题目要求总长度线性，所以需要提前得到：

```text
prefixPalindrome[len]
suffixPalindrome[pos]
```

分别表示：

```text
word[0 .. len-1] 是否为回文
word[pos .. n-1] 是否为回文
```

使用 **Manacher** 可以 `O(L)` 得到一个单词的全部这些信息。

# 3. C++17 实现

下面代码还特别优化了 Trie 的内存。

如果直接写：

```cpp
int next[26];
```

最多有：

```text
5000 × 300 = 1,500,000
```

个 Trie 节点，`26` 个 `int` 会消耗非常大的内存。

所以这里使用 **邻接链表式稀疏 Trie**。因为字符集只有 26 个字母，每次最多检查 26 条边，仍然属于 `O(S)`。

# 4. 用示例理解

例如：

```text
words = ["abcd", "dcba", "lls", "s", "sssll"]
```

Trie 中存的是反转后的：

```text
abcd  -> dcba
dcba  -> abcd
lls   -> sll
s     -> s
sssll -> llsss
```

查询：

```text
"abcd"
```

正序走 Trie：

```text
a -> b -> c -> d
```

恰好能够匹配：

```text
reverse("dcba") = "abcd"
```

所以得到：

```text
(0, 1)
```

即：

```text
"abcd" + "dcba"
= "abcddcba"
```

---

再看：

```text
"s" + "lls"
```

查询 `"s"`。

Trie 中 `"lls"` 被反转成：

```text
"sll"
```

查询 `"s"` 后已经匹配完成。

而 `"lls"` 剩余的前缀：

```text
"ll"
```

是回文，因此 `"lls"` 会存在当前节点的 `palList` 中。

于是得到：

```text
(3, 2)
```

对应：

```text
"s" + "lls"
= "slls"
```

# 5. 空字符串为什么也能正确处理？

例如：

```text
["a", ""]
```

因为：

```text
"a"
```

本身就是回文，所以：

```text
"a" + "" = "a"
"" + "a" = "a"
```

都成立。

在我们的 Trie 中：

- 空字符串结束在根节点；
- 一个完整字符串如果本身是回文，会被加入根节点的 `palList`。

因此：

查询 `"a"` 时，在根节点发现空字符串：

```text
"a" 剩余整体是回文
```

得到：

```text
[0,1]
```

查询 `""` 时直接查看根节点 `palList`，找到 `"a"`：

```text
[1,0]
```

所以无需专门对空串写特判。

## 6. 复杂度

设：

```text
S = Σ words[i].length
K = 回文对数量
```

### Manacher

每个字符串：

```text
O(length)
```

总计：

```text
O(S)
```

### 建 Trie

每个字符只处理一次。

由于每个节点最多只有 26 条边，稀疏 Trie 查找儿子的代价最多是常数 `26`：

```text
O(S)
```

### 查询 Trie

同理：

```text
O(S + K)
```

所以总复杂度：

```text
时间：O(S + K)
空间：O(S)
```

这已经是这道题在需要输出全部答案情况下的最优量级。

这题最容易写成的普通 **哈希表 + 枚举切分点** 解法通常是 `O(S × 最大单词长度)`；题目特意强调线性复杂度，本质上就是在要求把“每个切分位置是否为回文”也优化到线性预处理。
