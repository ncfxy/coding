# 字典树

**字典树**，也叫**前缀树**（Prefix Tree）或 **Trie树**（读作“try”），是一种专门用于**快速检索字符串**的多叉树数据结构。它的核心思想是用空间换时间，利用字符串的**公共前缀**来减少查询时间，最大限度地减少无谓的字符串比较。

为了让你直观理解，我们可以看一个例子。假设我们插入了三个单词：`"cat"`、`"car"` 和 `"dog"`，字典树的结构如下：

-   根节点（空）分叉出 `c` 和 `d`。
-   `c` 节点下分叉出 `a`。
-   `a` 节点下分叉出 `t` 和 `r`。

```
        (根)
       /   \
      c     d
      |     |
      a     o
     / \    |
    t   r   g
```
（每个节点通常会有一个布尔标记，表示该节点是否为一个单词的结尾，比如 `t` 和 `r` 都是结束节点）

---

### 1. 核心特点
-   **根节点为空**：不存储任何字符。
-   **路径代表单词**：从根节点到某个节点所经过的字符连起来，就是该节点对应的字符串（前缀）。
-   **子节点按字符存储**：每个节点的子节点通常用哈希表或数组存储，查找下一个字符的时间复杂度为 O(1)。

---

### 2. 主要操作及时间复杂度
假设待操作的字符串长度为 **L**：

-   **插入（Insert）**：从头遍历字符串的每个字符，若路径不存在则新建节点，最后标记结尾。时间复杂度：**O(L)**。
-   **查找（Search）**：从头遍历字符，若中途缺失或结尾标记不匹配，则不存在。时间复杂度：**O(L)**。
-   **前缀查询（StartsWith）**：判断字典树中是否有以某前缀开头的单词。时间复杂度：**O(L)**。

相比于哈希表（HashMap），字典树在**前缀查询**上具有绝对优势（哈希表需要遍历所有键），且**不存在哈希冲突**。

---

### 3. 优缺点

-   **优点**：
    -   **高效前缀匹配**：极其适合自动补全、拼写检查。
    -   **节省空间（有共享前缀时）**：存储大量相似词（如 `"test"`, `"testing"`, `"tested"`）时非常省内存。
-   **缺点**：
    -   **内存消耗大**：如果子节点使用数组（如长度为26的数组），大量节点会造成严重的空间浪费；如果使用哈希表，则会增加额外开销。
    -   **不适合精确查找**：如果只做精确的键值对查找，哈希表的效率（O(1)）通常优于字典树（O(L)）。

---

### 4. 经典应用场景

-   **搜索引擎/输入法的自动补全**：当你在搜索框输入“北京”，后台瞬间返回“北京大学”、“北京天气”等，底层常依赖 Trie 进行前缀匹配。
-   **拼写检查器**：检测单词是否在词典中，并找出编辑距离最近的候选词。
-   **IP 路由表查找（最长前缀匹配）**：路由器在匹配 IP 地址时，使用类似 Trie（基数树）的结构找到最长的匹配路由。
-   **敏感词过滤（DFA 算法）**：将敏感词库构建成 Trie 树，扫描文本时只需遍历一次即可找出所有敏感词，时间复杂度为 O(n)。

---

### 5. 进阶变体（补充）
为了解决内存过大的问题，工程上通常使用**压缩字典树（Radix Tree / Patricia Trie）**，它将只有一个子节点的链压缩成一个边（Edge），极大减少了节点数量。这种结构在 Redis（SDS 底层）和 Linux 内核中都有广泛应用。

**总结一句话**：字典树是处理**字符串集合**和**前缀相关**问题的利器，虽然占内存，但在自动补全和词频统计场景下，它是无可替代的基础数据结构。
